# 蒸馏检测与兜底路由（new-api）方案 v1

状态：待确认参数后开工
来源：把 hw_gateway 的「决策模型（训练数据与评测题库）」搬到 new-api，并复用 new-api 已有的「拒答降级 → 兜底渠道」机制。

---

## 1. 目标

Claude 渠道给用户后，有些用户会拿渠道去**蒸馏**（批量生产训练语料、评测集、RM 偏好数据）。检测到这类请求时：

1. 把该用户的流量**临时切到兜底渠道**（与拒答降级同一套重导机制）；
2. 记录**命中请求编号**（request id），运营可直接拿编号通知客户；
3. 发**告警**（Telegram + 企业微信）。

检测默认开启，但**只有该用户每分钟请求量达到阈值才激活**，避免对普通用户白花判定成本。

## 2. 复用与新增

| 能力 | 来源 | 处理 |
|---|---|---|
| 判定题库（训练数据与评测 4 题） | hw_gateway `decision_model` | 只迁这一库，题目文本原样搬 |
| 判定打分 | hw_gateway 的 Jev 调用 | 移植成 Go 服务，new-api 里单独配置端点/密钥/模型 |
| 窗口抽样 | new-api 拒答降级（Redis 滑窗） | 同一套窗口键结构，独立前缀 |
| 兜底渠道重导 | new-api `channel.FallbackChannelId` + distributor | 直接复用，不新建路由 |
| 用户级开关 | new-api `User.RefusalDemoteOverride`（三态） | 同款三态，新列 |
| 告警 | new-api `log_alert`（TG + 企微）／`overload_tg_notifier` | 复用发送通道，新增独立开关与文案 |
| 命中流水 | 新建表 | `distill_detect_hits` |

## 3. 判定链路

```
请求进入 → 文本类 relay？(现有 IsTextClassRelayFormat)
        → 用户三态开关允许？(跟随全局/强制/关闭)
        → 该用户每分钟请求数 ≥ 激活阈值？
        → 本次是否落在抽样桶首条？(每用户每 10 分钟最多判 1 次；已降级期间跳过)
        → 取样正文（头部 4000 字符，与 hw_gateway document.rs 一致）
        → 调 Jev 打分（4 题，取最高分）
        → 最高分 ≥ 判定阈值 → 命中
              ├─ 写 hits（request_id、user、score、题库、时间）
              ├─ 置降级标记（TTL = 降级时长）
              └─ 发告警（每轮降级一次）
        → 命中后，该用户后续请求由 distributor 重导到兜底渠道（现有逻辑）
```

关键点：

- **判定在响应前还是后**：与 hw_gateway 一样在**请求进入时**判（用请求正文），命中后从**本次请求**就开始走兜底，而不是等下一条。
- **不影响计费口径**：重导保持原分组计费（现有 `pickFallbackChannelGroup` 行为）。
- **兜底缺失**：未配「蒸馏兜底渠道」或该渠道不可用 → 直接 **429**，错误码 `distill_fallback_unavailable`，文案与拒答降级不同，运营一眼能分清；同时写一条 hits（`fallback_id=0`）并发告警。

## 4. 配置项（系统管理 → 安全与限制 → 拒答降级 下方新增「蒸馏检测」）

| 项 | 默认 | 说明 |
|---|---|---|
| 总开关 | 开 | 关闭后不抽样、不判定、不重导 |
| 每分钟请求量激活阈值 | 20 | 低于此值不判定 |
| 判定间隔 | 30s | 同一用户 30 秒最多判 1 次（每分钟上限 2 次） |
| 命中确认次数 | 4 | 确认窗口内累计命中 N 次才真正降级；未达到只写 hits |
| 确认窗口 | 5 分钟 | 滑动计数、不清零，超窗过期；p 掉时可调到 10 分钟 |
| 判定阈值 | 0.60 | 四题最高分 ≥ 该值即命中（与 hw_gateway 现网一致） |
| 降级时长 | 3600s | 与拒答降级一致 |
| 题库 | 仅「训练数据与评测」 | 4 题，可单独禁用题 |
| Jev 端点 / 密钥 / 模型 | 空 | new-api 自己配，不复用 hw_gateway 的库 |
| 告警 Telegram | 关 | 复用现有 TG 通道配置 |
| 告警企业微信 | 关 | 复用 log_alert 的企微群机器人 |
| 蒸馏兜底渠道 | 空 | **全局单选一个渠道**，与拒答降级的兜底完全独立；未配置=兜底不可用 |
| 兜底不可用时返回 429 | 固定 | 固定行为：429 + 独立错误码 `distill_fallback_unavailable`，文案与拒答降级区分 |

## 5. 用户级开关（用户编辑 → 拒答降级覆盖 下方）

「蒸馏检测」三态：

- 跟随全局（默认）
- 强制启用（即便全局关闭也判）
- 关闭（豁免该用户）

## 6. 数据表

```sql
CREATE TABLE IF NOT EXISTS distill_detect_hits (
  id            BIGSERIAL PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  request_id    TEXT NOT NULL,           -- 运营拿去通知客户的编号
  model         TEXT,
  channel_id    BIGINT,
  fallback_id   BIGINT,                  -- 实际重导到的渠道，0=未重导
  score         DOUBLE PRECISION NOT NULL,
  bank_id       TEXT NOT NULL,           -- 目前恒为 train
  categories    JSONB,                   -- 四题逐题分数
  doc_chars     INT,                     -- 取样字符数
  sampled_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  demote_until  TIMESTAMPTZ
);
CREATE INDEX ON distill_detect_hits (user_id, sampled_at DESC);
CREATE INDEX ON distill_detect_hits (request_id);
```

管理端新增「蒸馏命中记录」页：按用户 / 时间筛选，显示 request_id（一键复制）、分数、是否已重导、告警是否发出。

## 7. 告警文案（每轮降级只发一次）

```
[蒸馏检测] 用户 <id/name> 命中
请求编号: req_xxx
分数: 0.87（阈值 0.60）
渠道: 12 → 兜底 88
时间: 2026-11-19 20:00:00
```

Telegram 与企业微信可各自开关；发送失败只记日志，不影响重导。

## 8. 成本控制

- 只有达到每分钟请求量阈值的用户才判；
- 已降级中的用户跳过判定（一轮只花一次）；
- 同一用户同一正文哈希 10 分钟内不重复打分（内存 LRU + 可配 TTL）；
- 判定调用有超时（5s）与失败兜底：**判定失败一律按未命中放行**，不阻断用户。

## 9. 灰度

1. **观察期**：只记录 hits 与告警，**不重导**（配置项「只观察」）。
2. 观察 24–72 小时后看命中名单与误伤，确认阈值。
3. 打开重导。

## 10. 参数与已定事项（2026-11-19）

用户已定：

1. **命中后从当前请求就切兜底**（不等下一条）。
2. **兜底渠道单独配置**：不复用各渠道的 `FallbackChannelId`，也不复用拒答降级的兜底；蒸馏检测卡片里全局选一个渠道。命中后该用户流量整体导到这个渠道。
3. **兜底不可用 = 429**，错误码 `distill_fallback_unavailable`，message 与拒答降级不同，运营可据此判断是蒸馏检测兜底。
4. **Jev 密钥由用户自己在管理页保存**，代码与文档不留默认值、不写死任何密钥。
5. **先灰度**：只记录 + 告警，不重导；观察 24–72 小时后再开重导。

待 Hermes-aiyun 用线上数据回填（不拍脑袋）：

6. **每分钟请求量激活阈值 = 20 rpm**（线上 105 个用户里 p95 ≥20 的 26 个覆盖 95.6% 流量；20 是用户 p50 均值 10.2 的两倍，正常单机用户不会长期到 20/min）。
7. **判定间隔 30 秒**（每分钟最多 2 次）、**确认 4 次命中**才降级、确认窗口 5 分钟（滑动计数、不清零）。实测 ≈**28,657 次 Jev 调用/日**，用户已确认成本可接受（见 §11）。

## 11. 成本模型与实测（Hermes-aiyun，线上 24h 数据）

线上最近 24 小时 Claude 流量：**1,571,983 请求 / 105 个用户**。

按「请求抽样」实测（单位 次/日）：

| 阈值 T | N=10 | N=20 | N=40 |
|---|---|---|---|
| 20 rpm | 147,708 | 77,814 | 41,565 |
| 50 rpm | 118,488 | 60,704 | 32,037 |

最省的 T=50/N=40 也要 3.2 万次/日。原因是「每用户每分钟首条必判」这一项本身就有 1.4 万次/日的量级，请求抽样路线不成立。

改为**时间桶抽样**（每激活用户每桶只判桶内首条）实测：

| 阈值 T | 10 分钟桶 | 30 分钟桶 | 1 小时桶 |
|---|---|---|---|
| 5 rpm | 4,003 | 1,594 | 912 |
| 20 rpm | 2,085 | 831 | 466 |
| 30 rpm | 1,708 | 698 | 391 |
| 50 rpm | 1,057 | 451 | 267 |

定默认：**T=20 rpm + 10 分钟桶**，≈2,085 次/日。

### 最终方案（30 秒判定 + 4 次确认）实测

同一用户 30 秒最多判 1 次（每分钟上限 2 次），5 分钟窗口内累计 4 次命中才降级：

| 阈值 T | 日判定次数 | 激活用户数 |
|---|---|---|
| 10 rpm | 40,582 | 66 |
| 20 rpm | 28,657 | 47 |
| 30 rpm | 21,465 | 35 |
| 50 rpm | 12,722 | 24 |

T=20 时每个激活用户分钟平均判到 1.99 次（30 秒桶基本都满）。成本高的根因是流量集中：top3 用户占 58.8%，都是持续型 Agent 平台，一直在 20 rpm 以上；「要求连续 3–5 分钟都 ≥20」也收不窄（sustained_5min 仍有 21,182 次/日）。**用户已确认 28,657 次/日的成本可接受。**

确认速度：真语料离线回放单次命中率 p≈0.9（9/10 命中，分数 0.66–0.86），4 次约需 2–3 分钟，5 分钟窗口够用；若题库漂移让 p 掉到 0.5 以下，5 分钟固定窗口会漏掉大半，因此窗口实现为**滑动计数、不清零**，必要时调到 10 分钟。

可选的进一步降本杠杆（**未默认启用**，需用户点头）：单次只送正文头部 4k、只上 2 道题，单次成本约降到 40%，同样预算可把桶压到 5 分钟（T=20 时约 4,000 次/日）。

口径：单日样本，周末/工作日差异未覆盖；`request_metrics_logs.created_at` 按请求完成时间归桶。

## 12. 开工顺序

1. 观察模式跑通（判定服务 + hits 表 + 告警 + 管理页），不接重导；
2. 观察期数据回来确认阈值与误伤；
3. 打开重导 + 429 兜底。

**第 3 步的硬要求**：观察模式下判定放在响应返回后的后台 goroutine 里（不拖慢用户请求）；打开重导前必须把判定挪到分发**之前**同步执行，否则「命中的这一次请求」走不到兜底，与 §3 的链路矛盾。实现位置见 `router/relay-router.go` 中间件顺序处的注释。

## 13. 已知缺口（Reviewer 首轮审查，2026-11-19）

1. **Gemini 原生流量漏判**：检测中间件只挂在 `relayV1Router` 的文本路径白名单上，`/v1beta/models`、`/pg` 是独立 router，没挂这个中间件；`/pg/chat/completions` 是死条目。当前版本不修，记入待办。
2. **Redis 不可用时多实例重复判定**：`takeBucket` / `dedupSeen` / `recordConfirm` 的进程内兜底各实例独立，Redis 挂时同一用户最多被 2N 次/分判定（成本问题，不是正确性问题）。观察期只多花钱；切重导后确认会更晚，偏安全。
3. 已在当轮修掉：dedup 时序（改到判分成功后写键）、告警节流、用户缓存 schema 升版 + 编辑后立即刷新、内存 dedup 过期清理。

## 14. 题库可编辑 + 独立 TG 告警（2026-11-20 用户追加）

### 14.1 题库从四个开关变成可编辑列表

现状：四道题的题面写死在判定服务里，管理页只有四个开关键。

改为：题库是**数据**，不是代码。

```go
type DistillQuestion struct {
    ID      string `json:"id"`      // [a-z0-9_]{1,32}，唯一
    Name    string `json:"name"`    // 展示用短名，1..64
    Prompt  string `json:"prompt"`  // 题面正文，1..8000 字符
    Enabled bool   `json:"enabled"`
}
```

- 默认值 = hw_gateway「训练数据与评测」题库的 4 题，**题面逐字照搬**：`corpus_farm`、`reward_rl`、`judge_eval`、`distill_target`（搬运时从 hw_gateway 代码/配置取原文，不要重写、不要压缩）。
- 存在 `DistillDetectSetting.Questions []DistillQuestion`，随配置一起走 options 表，**不动表结构**。
- 管理页要能：看到每题完整题面、单题编辑、单题启停、新增、删除、调整顺序。
- 校验（后端强制，前端同步）：题目总数 1..20；`id` 唯一且匹配 `[a-z0-9_]{1,32}`；`name` 1..64；`prompt` 1..8000；**至少 1 题启用**（全关直接拒绝，别让判定静默失效）。
- 判定：**一次请求带全部启用题**（与 hw_gateway 的 `questions_payload` 一致，也是 §11 成本模型「一次判定 = 1 次调用」的前提），Jev 一次回全部 answers，取最高分与 `threshold` 比较；命中记录 `categories` 存 `{题目id: 分数}`。**不要逐题各发一次**——那会把 28,657 次/日翻到 4 倍。整体超时用 `jev_timeout_ms`。
- 旧的四个 `question_*` 布尔字段**废弃删除**（迁移时把它们的 true/false 映射成对应题目的 `enabled`），GET/PUT 都不再出现这四个字段。

### 14.2 Telegram 告警独立通道

现状：复用 `log_alert` 的 TG 配置。改为独立配置：

| 字段 | 说明 |
|---|---|
| `tg_bot_token` | 独立 bot 的 token；**不回显**，GET 只返回 `tg_bot_token_set: bool`；PUT 留空=不修改，`"__clear__"`=清空 |
| `tg_chat_id` | 目标群/频道的 chat id，字符串 |

- 不复用、不读取现有通知通道的任何配置；两套互不影响。
- 企业微信那条已经是独立 webhook（`wecom_webhook_url`），保持不变。
- 两个通道都未配置时，命中只写 hits，不发告警，不报错。
- 新增 `POST /api/distill_detect/alert_test`：用当前配置发一条测试消息，返回各通道的实际结果（发送成功/未配置/失败+原因），便于运营配完当场验。

## 15. 蒸馏兜底按兜底分组计费（2026-11-20 用户提出）

现状：蒸馏命中后 `Distribute` 换渠道，但 `relayInfo.UsingGroup` 仍是原分组，结算走原分组倍率 —— 用户实际用上了兜底渠道，却按原渠道价格扣费。拒答降级也有同样问题，但本次只修蒸馏，拒答那条单独立项。

### 15.1 规则

命中重导到兜底渠道（且真的换了渠道）后，本次请求的计费分组改为**兜底渠道的分组**：

1. 取兜底渠道的 `Group` 字段（逗号分隔）。
2. 若原 `UsingGroup` 在兜底渠道的分组列表里，用它（价格最贴近用户原意）。
3. 否则取兜底渠道分组列表中第一个**已配置倍率**的分组（`ratio_setting.ContainsGroupRatio` 为真）。
4. 兜底渠道无分组、或所有分组都没配倍率 → 维持原 `UsingGroup` 不变，并写一条 warn 日志（说明这笔按原分组计费）。
5. 记住值的不是渠道 id，是**结算用的分组名**：`relayInfo.UsingGroup` 换成上面选中的分组，`PriceData.GroupRatioInfo` 随之重算（不能沿用换渠道前算好的价格）。
6. 日志 `other` 里加两个字段：`distill_fallback_group`（实际计费分组）、`distill_origin_group`（原分组），便于对账。
7. 只改计费口径，不碰倍率配置本身、不改渠道分组。

### 15.2 边界

- **拒答降级那条路径一个字都不动**：它命中后仍按原渠道/原分组价格计费，这是明确的产品口径，不是漏改。不许因为共用 `Distribute` 就把分组替换做成通用行为。
- 未命中/确认次数不足/观察模式：完全不变，不写这两个字段。
- 兜底渠道 == 原渠道（自环）：不重算，按原分组计费。
- 计费分组改了之后，预扣/结算/日志三处必须用同一个分组，不能一处新一处旧 —— 这条要有测试。

### 15.3 验收

一条命中请求打到兜底渠道后：`distill_detect_hits` 里能看到兜底渠道 id；对应 `logs` 行的 `other.group_ratio` 等于兜底分组的倍率，而不是原分组倍率；`other.distill_fallback_group` 与之一致。
