# 商务合作与上游管理统一开发计划

## 1. 文档目的

本文档将“商务合作申请”和“管理员上游管理”两组原型统一为一个完整功能，覆盖：

- 合作方提交中转站申请并查看审核进度。
- 管理员录入、筛选和维护候选上游。
- 管理员对后台录入或合作方自行录入的上游执行压测。
- 按统一基准计算指标得分和综合得分。
- 管理员手动同步或按规则自动同步到正式渠道。
- 将管理员处理结果同步回合作方申请状态。

本文档是后续数据库、后端、前端、测试和验收的统一实现依据。当前第二组原型明确定位为管理员功能；第一组“商务合作”页面定位为合作方功能。

## 2. 功能边界与角色

### 2.1 合作方

合作方只能管理自己提交的商务合作申请：

- 新增申请。
- 在待审核状态编辑或删除申请。
- 查看申请状态和允许公开的压测结果。
- 审核失败后修改资料并重新提交。
- 不得直接发起压测、修改基准、同步渠道或查看 API 密钥原文。

### 2.2 管理员

管理员通过“上游管理”页面统一处理两类候选上游：

- `后台录入`：管理员直接新增的候选上游。
- `自行录入`：由合作方商务合作申请自动生成的候选上游。

管理员可按权限执行新增、编辑、压测、查看详情、同步渠道、配置基准和配置自动同步。只有具备相应敏感权限的管理员可以处理 API 地址、API 密钥和渠道同步。

### 2.3 首期范围

- 首期支持 OpenAI 和 Gemini 类型，类型值复用现有渠道类型常量。
- 首期使用一个名为“通用”的压测基准。
- 首期同一时间全局只运行一个候选上游压测任务，避免压测流量影响网关正常请求。
- 首期不因复测分数下降自动禁用已经同步的正式渠道。
- 不修改 `relaykit/` 的独立模块边界；压测编排放在根模块的 `service/` 中。
- 压测执行不运行在 API/Web Pod 内，首期部署为独立的 `upstream-benchmark-worker` Pod；API Pod 只负责创建任务、查询状态和展示结果。

### 2.4 独立实现与最小侵入原则

本功能按全新业务域实现。申请、候选上游、压测、评分和同步编排不得通过给现有渠道流程增加来源判断或状态分支来实现。

- 模型、DTO、service、controller、router、authz 资源、SystemTask handler、前端 feature 和测试均使用独立模块。
- 现有模块只允许增加必要的注册入口，不改变已有接口、状态、响应结构、缓存语义和页面交互。
- 不在现有渠道 CRUD、渠道测试、定时渠道测试、渠道页面或 relay 请求链路中增加本功能分支。
- 复用现有代码时只依赖职责稳定、契约匹配的底层能力；不得从 service 调用 controller，也不得为方便本功能改变现有公共函数语义。
- 本功能应可通过移除独立路由、任务和导航注册而停用，停用后现有渠道工作流保持原样。

## 3. 核心业务模型

统一功能拆成三个业务对象，避免把“申请审核状态”“上游压测状态”和“正式渠道状态”混成一个字段。

### 3.1 商务合作申请

记录合作方的申请和审核结果，仅适用于自行录入来源。

| 字段 | 说明 |
| --- | --- |
| `id` | 申请 ID |
| `user_id` | 提交用户 ID |
| `upstream_id` | 关联候选上游 ID，一对一 |
| `status` | 申请审核状态 |
| `reject_reason` | 审核失败原因 |
| `revision` | 重新提交版本号 |
| `created_time` | 首次提交时间 |
| `updated_time` | 最近修改时间 |
| `submitted_time` | 最近提交时间 |
| `reviewed_time` | 最近审核完成时间 |

申请状态：

| 状态值 | 页面文案 | 说明 |
| --- | --- | --- |
| `pending_review` | 待审核 | 已提交，尚未开始压测 |
| `benchmark_running` | 压测中 | 管理员已发起压测 |
| `pending_decision` | 审核中 | 压测完成，等待管理员处理 |
| `approved` | 审核通过 | 已同步到正式渠道 |
| `rejected` | 审核失败 | 管理员已标记压测未通过 |

### 3.2 候选上游

管理员“上游管理”页面的主数据对象，后台录入和自行录入共用同一张表。

| 字段 | 说明 |
| --- | --- |
| `id` | 候选上游 ID |
| `source` | `admin` 或 `self` |
| `owner_user_id` | 自行录入时的用户 ID，后台录入为空 |
| `application_id` | 自行录入时关联申请 ID，后台录入为空 |
| `type` | 上游类型，复用现有渠道类型值 |
| `name` | 名称 |
| `base_url` | API 地址 |
| `normalized_base_url` | 用于唯一性判断的规范化地址 |
| `api_key` | 压测及同步渠道使用的密钥，接口不得返回原文 |
| `contact` | 联系方式 |
| `remark` | 备注 |
| `benchmark_status` | `pending`、`running`、`completed` |
| `latest_run_id` | 最近一次压测记录 ID |
| `channel_id` | 同步生成的正式渠道 ID，未同步为空 |
| `synced_time` | 最近同步时间 |
| `created_time` | 创建时间 |
| `updated_time` | 修改时间 |

约束：

- `type + normalized_base_url` 构成全局联合唯一约束，两种来源不可重复录入同一类型和地址。
- API 地址规范化处理协议和主机大小写、默认端口、尾部斜杠；原地址仍保留用于展示和请求。
- 列表和详情只返回 `has_api_key`，不返回 `api_key`。
- 编辑时密钥为空表示保留原密钥，不允许用掩码覆盖真实密钥。
- “是否正式使用”以 `channel_id` 是否存在为准。该字段表示已经完成过渠道同步，不随渠道后续启用或禁用状态反向变化。

### 3.3 压测记录

每次压测都创建独立历史记录，候选上游只保存最近一次记录引用。

| 字段 | 说明 |
| --- | --- |
| `id` | 压测记录 ID |
| `upstream_id` | 候选上游 ID |
| `system_task_id` | 后台任务 ID |
| `status` | `pending`、`running`、`succeeded`、`failed` |
| `model` | 压测模型 |
| `concurrency` | 并发数 |
| `profile_name` | 基准名称，首期为“通用” |
| `profile_version` | 基准版本 |
| `profile_snapshot` | 发起压测时的基准快照，TEXT JSON |
| `metrics` | 聚合后的原始指标，TEXT JSON |
| `scores` | 按基准计算的逐项得分，TEXT JSON |
| `status_code` | 探测请求 HTTP 状态码 |
| `latency_ms` | 探测请求延迟 |
| `overall_score` | 综合得分，0 到 100 |
| `unmet_count` | 未达到准入线的指标数量 |
| `auto_sync_status` | 自动同步状态：`skipped`、`succeeded`、`failed` |
| `auto_sync_error` | 自动同步失败原因，必须脱敏 |
| `auto_synced_time` | 自动同步完成时间 |
| `started_time` | 开始时间 |
| `finished_time` | 结束时间 |
| `duration_ms` | 压测耗时 |
| `error` | 技术失败原因，必须脱敏 |

只保存聚合指标、错误分类和必要样本计数，不保存上游响应正文和 API 密钥。

### 3.4 基准配置

新增压测基准配置模型 `UpstreamBenchmarkProfile`：

- `name`：基准名称，首期固定为 `general`。
- `version`：每次保存成功后递增。
- `metrics`：TEXT JSON，保存固定指标的准入线、满分线和权重。
- `updated_time`、`updated_by`：更新时间和管理员 ID。

固定指标：

- `RPM`
- `TPM`
- `TTFT_P50_8K`
- `TTFT_P90_8K`
- `TTFT_P50_32K`
- `TTFT_P90_32K`
- `TTFT_P50_128K`
- `TTFT_P90_128K`
- `OTPS_P50_128K`

准入线、满分线和权重全部为空时表示该指标未启用；部分填写视为非法。至少启用一个指标。

### 3.5 自动同步配置

通过项目现有 Option/setting 机制保存：

- `UpstreamAutoSyncEnabled`：默认关闭。
- `UpstreamAutoSyncChannelTag`：同步渠道标签。
- `UpstreamAutoSyncMinScore`：自动同步最低综合得分。

开启时必须同时填写标签和分数阈值。页面在开关旁展示当前标签和阈值。

## 4. 状态机与跨模块联动

### 4.1 自行录入完整流程

```text
合作方新增申请
  -> 申请 pending_review
  -> 候选上游 pending / source=self

管理员发起压测
  -> 申请 benchmark_running
  -> 候选上游 running
  -> 压测记录 running

压测正常完成
  -> 申请 pending_decision
  -> 候选上游 completed
  -> 保存压测结果与得分

管理员手动同步渠道，或命中自动同步规则
  -> 创建正式渠道并默认启用
  -> 回写 channel_id
  -> 申请 approved

管理员标记“压测未通过”
  -> 申请 rejected
  -> 候选上游保留 completed 和压测历史

合作方修改并重新提交
  -> 申请 revision + 1，状态 pending_review
  -> 更新原候选上游，状态重置为 pending
  -> 历史压测记录保留
```

### 4.2 后台录入完整流程

```text
管理员新增上游
  -> 候选上游 pending / source=admin

管理员发起压测
  -> running

压测完成
  -> completed

管理员手动同步渠道，或命中自动同步规则
  -> 创建正式渠道并默认启用
  -> 回写 channel_id
```

后台录入没有商务合作申请和审核状态，也不提供“压测未通过”操作；管理员可以保留结果后复测。

### 4.3 技术失败处理

连接超时、后台任务崩溃、锁丢失或结果无法解析属于技术失败，不等同于压测未达标：

- 压测记录标记 `failed` 并保存脱敏错误。
- 候选上游由 `running` 恢复为 `pending`。
- 自行录入申请由 `benchmark_running` 恢复为 `pending_review`。
- 页面提示失败原因并允许重新发起压测。

性能指标低于准入线仍属于一次成功完成的压测，候选上游状态为 `completed`。

## 5. 页面与交互计划

### 5.1 合作方“商务合作”页面

路由建议：`/_authenticated/business-cooperation/`，放入 Personal 导航分组。

页面内容：

- 顶部展示合作说明、审核依据、密钥用途和处理结果说明。
- 支持按名称、类型和申请状态筛选。
- 表格字段：名称/API 地址、类型、申请状态、最近压测耗时、最近压测得分、创建时间、操作。
- 新增和编辑使用同一表单，字段包括类型、名称、API 地址、API 密钥、联系方式和备注。
- 类型、名称、API 地址、API 密钥、联系方式必填；备注选填。
- 删除使用二次确认。
- 详情展示综合得分、耗时、开始/结束时间、模型、基准和逐项指标。

合作方操作矩阵：

| 申请状态 | 编辑 | 删除 | 详情 | 重新提交 |
| --- | --- | --- | --- | --- |
| 待审核 | 是 | 是 | 否 | 否 |
| 压测中 | 否 | 否 | 否 | 否 |
| 审核中 | 否 | 否 | 是 | 否 |
| 审核通过 | 否 | 否 | 是 | 否 |
| 审核失败 | 否 | 否 | 是 | 是 |

审核中允许查看已经生成的压测结果，但不得查看管理员内部错误、任务执行器、API 密钥或渠道内部字段。

### 5.2 管理员“上游管理”页面

路由建议：`/_authenticated/upstreams/`，放入 Admin 导航分组。

#### 顶部工具栏

- 名称模糊搜索。
- 类型筛选。
- 是否正式使用筛选。
- 得分比较符和得分输入框，首期支持 `>=`、`<=`。
- 压测状态筛选。
- 待压测数量和正式使用数量摘要。
- 批量“同步到渠道”。
- “新增上游”。
- “基准线配置”。
- 自动同步开关及当前渠道标签、最低得分展示。

#### 表格

字段按原型实现：

- 全选。
- 名称、API 地址和来源徽标。
- 类型。
- 是否正式使用。
- 最近压测开始时间。
- 最近压测耗时。
- 最近压测得分及未达标项数量。
- 最近压测状态。
- 创建时间。
- 联系方式。
- 备注。
- 操作。

默认按创建时间倒序；列表使用服务端分页，页面大小复用项目表格规范并限制最大 100。

#### 管理员操作矩阵

| 来源 | 压测状态 | 已同步 | 可用操作 |
| --- | --- | --- | --- |
| 后台录入 | 待压测 | 否 | 编辑、压测 |
| 后台录入 | 执行中 | 否/是 | 无修改操作 |
| 后台录入 | 已完成 | 否 | 详情、压测、同步到渠道 |
| 后台录入 | 已完成 | 是 | 详情、压测 |
| 自行录入 | 待压测 | 否 | 压测 |
| 自行录入 | 执行中 | 否/是 | 无修改操作 |
| 自行录入 | 已完成且审核中 | 否 | 详情、压测、同步到渠道、压测未通过 |
| 自行录入 | 已完成且审核通过 | 是 | 详情、压测 |
| 自行录入 | 已完成且审核失败 | 否 | 详情，等待合作方重新提交 |

补充规则：

- 编辑仅允许“后台录入 + 待压测”。所有字段均可修改，API 密钥留空表示不变。
- 压测允许“待压测”和“已完成”；已完成记录再次压测会生成新历史记录。
- 详情仅在存在成功完成的压测记录时开放。
- 手动同步同时支持后台录入和自行录入，要求已完成且未同步。
- “压测未通过”只允许自行录入、审核中、已完成且未同步的数据。
- 已同步记录复测分数下降时不自动禁用或删除正式渠道。

### 5.3 新增/编辑上游

字段：

- 类型，必填。
- 名称，必填。
- API 地址，必填。
- API 密钥，新增必填、编辑可留空。
- 联系方式，选填。
- 备注，选填。

后台新增记录的来源固定为“后台录入”，前端不可修改来源。

### 5.4 发起压测

表单字段：

- 压测模型，必填。通过后台按上游类型和凭据获取可用模型；获取失败时返回明确错误，不允许前端自行伪造类型不支持的模型。
- 并发数，必填，服务端强制校验允许范围。首期建议范围为 1 到 100，并允许通过后端配置收紧上限。

按钮提交后立即关闭弹窗、刷新列表并显示“执行中”。同一候选上游不得重复发起；全局已有压测运行时返回冲突和当前任务信息。

### 5.5 手动同步到渠道

- 行操作和批量操作共用同一接口。
- 仅允许选择“已完成 + 未同步”的候选上游。
- 填写渠道标签后提交。
- 批量同步先完整校验所有记录，再在一个事务内创建渠道；任意一条失败则全部回滚。
- 渠道默认启用，`group` 使用 `default`，`tag` 使用提交值。
- `test_model` 和初始 `models` 使用最近一次压测模型；同步完成后管理员可在现有渠道管理中获取或编辑完整模型列表。
- 自行录入同步成功后，同时将商务合作申请更新为审核通过。

### 5.6 自动同步到渠道

- 开关默认关闭。
- 开启时弹窗要求填写渠道标签和最低综合得分。
- 压测成功完成后，如果候选上游未同步且综合得分大于等于阈值，则调用与手动同步相同的服务。
- 自动同步只按综合得分阈值判断，不额外要求所有单项达到准入线；详情仍显示未达标项供管理员审计。
- 自动同步失败不回滚压测结果；记录脱敏错误并保留手动同步入口。
- 关闭自动同步后保留标签和阈值配置，但停止触发同步。

### 5.7 基准线配置与详情

基准配置使用固定指标表格，每行编辑准入线、满分线和权重。保存时验证：

- RPM、TPM、OTPS 为越大越好，满分线必须大于或等于准入线。
- TTFT 为越小越好，满分线必须小于或等于准入线。
- 已启用指标的阈值和权重必须为有限正数。
- 至少启用一个指标。

详情页展示：

- 综合得分和总耗时。
- 开始时间、结束时间、压测模型、渠道名称和基准名称。
- 指标、实测、准入线、满分线、权重、得分和压测结果。
- 未达到准入线的指标整行使用错误色强调；不能只依赖颜色，结果列必须同时显示“未达标”。

## 6. 压测与评分规则

### 6.1 指标定义

| 指标 | 单位 | 方向 |
| --- | --- | --- |
| RPM | 请求/分钟 | 越大越好 |
| TPM | Token/分钟 | 越大越好 |
| TTFT P50/P90 | 毫秒 | 越小越好 |
| OTPS P50 | 输出 Token/秒 | 越大越好 |

压测分为吞吐阶段和 8K、32K、128K 上下文延迟阶段，使用固定、可复现的请求样本。所有阶段共享所选模型和并发配置。响应正文不持久化。

### 6.2 越大越好的指标

设实测值为 `actual`，准入线为 `admission`，满分线为 `full`：

```text
actual < admission:
score = 60 * actual / admission

admission <= actual < full:
score = 60 + 40 * (actual - admission) / (full - admission)

actual >= full:
score = 100
```

当 `full == admission` 时，达到该值直接计 100 分，低于该值仍按第一段计算。

### 6.3 越小越好的指标

```text
actual > admission:
score = 60 * admission / actual

full < actual <= admission:
score = 60 + 40 * (admission - actual) / (admission - full)

actual <= full:
score = 100
```

当 `full == admission` 时，达到或低于该值直接计 100 分，高于该值仍按第一段计算。

### 6.4 综合得分

```text
综合得分 = sum(指标得分 * 指标权重) / sum(指标权重)
```

统一规则：

- 指标得分限制在 0 到 100。
- 缺失、NaN、无穷或负数实测值按 0 分处理并标记未达标。
- 单项得分低于 60 即为未达到准入线。
- 综合得分保留一位小数；数据库保留未格式化值。
- 压测记录保存基准快照，后续修改基准不得改变历史结果。

### 7.4 权限设计

在现有 `service/authz` 中新增 `upstream` 资源：

### 7.5 压测后台任务

压测采用 API/Web 与 Worker 分离的部署模型。API/Web Pod 不执行压测 handler，只创建和查询持久化的 `SystemTask`；新增独立的 `upstream-benchmark-worker` 进程和 Pod，专门领取并执行 `upstream_benchmark` 任务：

- Payload 保存候选上游 ID 和压测记录 ID，不保存 API 密钥。
- API 创建任务后将状态置为待领取，Worker 通过任务类型过滤领取，不允许 API 进程内联执行或兜底执行该任务。
- Worker handler 执行前重新读取候选上游和基准快照；API 密钥只在 Worker 运行时从受控存储读取，不进入任务 payload、state、result 或日志。
- Worker 复用现有任务表、租约和心跳等稳定的持久化协调能力，但任务 handler 注册、进程启动和运行时配置均属于独立 Worker 模块。
- 首期 Worker Deployment 默认运行一个副本，并通过任务类型级唯一活动锁保证全局串行；后续扩容副本仍必须依赖租约避免重复执行。
- Worker 进度写入 `SystemTask.state` 和候选上游状态，管理员列表轮询候选上游状态，不直接依赖 Worker 内存数据。
- Worker 在持久化压测结果后再执行自动同步；处理完成、失败、超时、租约丢失和优雅退出都必须有明确的状态恢复路径。
- Worker Pod 不提供用户业务 API，不注册管理员路由，不加载前端资源；其网络、CPU、内存、超时和并发配置独立于 API/Web Pod。
- Worker 使用独立的部署配置、健康检查、日志字段和告警指标，至少监控待领取任务数、执行时长、失败数、租约续期失败和当前活动任务。

现有 `channel_test` 只做渠道健康检查，不承担吞吐量和长上下文性能压测，不能作为本功能的压测结果来源。

`upstream_benchmark` 使用独立 Worker handler 和 `service/upstream_benchmark.go` 完成全流程，不修改 `channel_test` 的触发条件、执行逻辑和结果 schema。需要复用通用 HTTP 或 provider 能力时，在新模块内增加适配器，并保持现有调用方行为不变。

#### Worker 模块与生命周期

建议新增 `cmd/upstream-benchmark-worker/` 作为 Worker 入口，并将 handler、领取循环、优雅退出和健康检查放在独立的 Worker 模块中。部署约束如下：

1. API/Web 与 Worker 使用可独立发布和回滚的镜像进程；Worker 镜像只包含执行压测所需的代码和配置。
2. Worker 通过数据库任务记录协调，不依赖 API Pod 的本地内存、进程锁或定时器；Pod 重启后可由租约过期机制恢复未完成任务。
3. Worker 只接受任务 ID 和候选上游 ID 等非敏感标识，密钥通过运行时受控读取获得，并遵循最小权限和出站网络策略。
4. Worker 版本与任务 schema 必须向后兼容；发布或回滚期间，旧 Worker 不得领取无法解析的新任务 payload。
5. Worker 无可用副本时，API 仍可创建任务并展示“待执行”，但不得把压测任务转回 API Pod 执行；运维告警负责提示积压。

### 7.6 渠道同步事务

同步逻辑集中在 `service/upstream_channel_sync.go`，不得调用渠道 controller，也不得修改现有渠道创建、更新接口的响应或前端行为。同步服务按以下顺序执行：

1. 按 ID 排序并锁定全部候选上游。
2. 校验全部记录已完成压测且未同步。
3. 创建 `Channel`，复制类型、名称、API 地址和 API 密钥。
4. 设置默认启用、默认分组、渠道标签、压测模型和测试模型。
5. 在同一事务中创建对应 `Ability`。
6. 回写每条候选上游的 `channel_id` 和 `synced_time`。
7. 自行录入来源同步申请状态为 `approved`。
8. 事务提交后刷新渠道缓存。
9. 写入不含密钥的管理员审计日志。

同步接口必须幂等：已存在 `channel_id` 时返回已有结果，不再创建第二条渠道。

同步服务只复用契约适用的 model/service 底层能力。若现有 `BatchInsertChannels` 无法加入调用方事务，则新增一个支持传入 `*gorm.DB` 的渠道领域函数，由上游同步服务调用；该函数使用可长期复用的渠道领域命名并保持原函数行为不变，不得通过修改原函数事务边界影响现有调用方。

### 7.7 安全要求

- 所有输入在前后端双重校验；并发数、字符串长度和分页大小设置硬上限。
- 自行录入地址执行 SSRF 校验并禁止访问私有、回环、链路本地和保留地址。
- 后台录入地址允许管理员按现有渠道策略配置受信任内部上游，但必须校验 `http/https` 协议并受敏感权限保护。
- API 密钥禁止出现在 URL、日志、审计参数、SystemTask payload/state/result、错误消息和 API 响应中。
- 详情接口只返回 `has_api_key`。
- 所有 JSON 编解码调用使用 `common.Marshal`、`common.Unmarshal` 等项目包装函数。
- 审计动作至少覆盖新增、编辑、发起压测、更新基准、更新自动同步、手动同步、自动同步和标记未通过。

- 通过脚本补齐七种语言。
- 执行后端测试、前端测试、类型检查、lint 和构建。
- 构建 Worker 镜像并验证独立 Pod 启动、健康检查、任务领取、租约续期、重启恢复和无 Worker 时的积压告警。
- 使用测试上游完成申请、压测、手动同步、自动同步、拒绝和重新提交的端到端验收。
- 对现有渠道 CRUD、连通性测试、定时测试、缓存和管理页面执行无变更回归，并核对既有模块 diff 仅包含批准的注册点。

## 11. 验收标准

功能完成必须同时满足：

1. 合作方可以完成新增、待审核编辑/删除、查看结果和失败后重新提交。
2. 管理员列表同时展示后台录入和自行录入，并正确显示来源、压测和正式使用状态。
3. 管理员只能在规定状态执行编辑、压测、详情、同步和压测未通过操作。
4. 压测由独立 `upstream-benchmark-worker` Pod 异步执行，API/Web Pod 不执行压测；刷新页面、多实例部署或 Worker 重启不会重复运行同一任务。
5. 评分严格符合本文公式，历史结果不受基准修改影响。
6. 手动和自动同步均只创建一个正式渠道，渠道默认启用并带指定标签。
7. 自行录入的同步与拒绝结果能够正确回写合作方页面。
8. API 密钥不出现在任何读取接口、任务数据、日志和错误消息中。
9. 所有数据库代码兼容 SQLite、MySQL 和 PostgreSQL。
10. 桌面端和移动端均可完成核心流程，新增文案支持全部七种前端语言。
11. 新功能代码位于独立模块，现有文件的业务逻辑 diff 为零，仅包含计划允许的注册代码和脚本生成的国际化键。
12. 现有渠道 CRUD、连通性测试、定时测试、缓存和管理页面通过原有回归；停用新功能注册后，现有渠道流程不受影响。
13. Worker Pod 可独立部署、扩缩容和回滚；无 Worker 时任务保持可恢复的待执行状态，不触发 API Pod 执行兜底。
14. Worker 发生崩溃、租约丢失或 Pod 重启后，任务能按租约规则恢复或进入明确失败状态，且不产生重复压测结果或重复渠道同步。

## 12. 已确认的统一决策

为消除两组原型中的歧义，本计划采用以下统一定义：

- 当前管理员原型页面名称为“上游管理”，不是合作方申请页面。
- 后台录入和自行录入都进入同一个管理员候选上游列表。
- 管理员列表的压测状态只有待压测、执行中和已完成；合作方页面单独维护审核状态。
- 手动或自动同步到渠道即代表自行录入申请审核通过。
- “压测未通过”即代表自行录入申请审核失败，后台录入不需要该动作。
- 两种来源都允许手动和自动同步渠道；原型中“同步到渠道仅后台录入”的文字与“来源：后台录入、自行录入”冲突，以支持两种来源为准。
- 审核中允许合作方查看已完成的压测结果。
- 自动同步只依据综合得分阈值；单项未达标继续在详情中明确展示。
- 已同步上游允许复测，但复测不自动改变正式渠道启用状态。
- 首次同步渠道的模型列表使用最近一次压测模型，完整模型列表在现有渠道管理中继续维护。
